# WP-R2-14 采集记录、操作记录与系统日志

基线 `78c09d9f96c27770c590d1f6760abb37938abec9`（监控卡片整合）。本包不新增表，也不改采集调度。

## 读模型

- 采集记录的一行是 `collector_jobs` 的一行。`pending` 且没有 `collector_runs` 时，耗时和写入数是空，不是 0。失败后被重新排队的仍是同一个 job，当前状态是排队，最近一次失败留在 `latestAttempt`。
- 已删除的 `monitor_targets` 仍按 `target_id` 连接，历史任务不丢。对象显示名优先用视频标题或 UP 主名称，否则用目标上的 label。
- 时间筛选按 `scheduled_for` 的 Asia/Shanghai 自然日，页面称「计划日期」。未传起止日期时默认最近 7 个自然日，响应里的 `range.defaulted` 标明这一点。23:50 计划、次日开始的任务落在计划日。
- 列表上的「尝试（已开始）」是 `collector_jobs.attempts`。抽屉里的「已完成执行记录」是 `collector_runs` 条数。运行中还没有 run 时，前者可以是 1，后者是 0。
- `group=target` 先按对象分页，再取每组有限条最近任务，并返回 `matchCount`。截断的一组不是该对象的完整历史。
- 任务详情里的请求和日志只来自该 job 的 run，或 `job_id` 匹配且没有 `run_id` 的日志。关联日志缺失时返回「暂无关联日志」或「关联日志已过保留期」，run 的成败不变。日志保留天数与任务表是两套数据。

## 操作记录

监控项的新增、暂停、恢复、频率、名称、标签、移除和手动采集，在产品 API 提交成功之后用现有 logger 写入 `app_logs`。info 白名单增加对应的 `monitor.target.*` 事件，logger 队列和 sink 实现没有改。

- 幂等「已存在」、校验失败、已删除后的拒绝，不写成功事件。
- patch 只记录真正发生变化的字段。只改标签不会记成恢复。
- 事件里保存目标类型、外部身份和名称快照，不保存请求体、Cookie 或 header。操作者没有单独的身份来源，所以 `actor` 为空，页面显示「未记录」。来源记为 `api`，因为这是 API 接受的动作。
- 写日志发生在事务提交之后。日志失败不会把已经提交的操作改成失败，也不会补一条假记录。这不是数据库级 exactly-once 审计。

## 页面

`/ops` 标题为「日志与诊断」。默认页签是采集记录。侧栏入口仍是运维诊断。`/ops?targetId&targetType&externalId` 在采集记录里按该对象筛选。监控页不再渲染「最近采集任务」，只留「查看采集记录」；卡片上的「查看日志」仍指向同一组参数。

系统日志默认展示所选时间范围内的入库日志，技术 JSON 默认折叠，成功的 HTTP 访问不进入列表。「只看告警和失败」要用户勾选，或 URL 显式带 `attention=1`，才会只留 warn/error。操作记录的日期按事件时间过滤，标签是「事件日期」。一个页签请求失败时，健康摘要和其他页签仍保留自己的状态。
